# 기능 스펙: FirstLook 브리핑 근거·상태 고도화

**기능 디렉터리**: `specs/002-firstlook-mvp-hardening/`
**작성일**: 2026-11-11
**상태**: 구현 중
**입력**: FirstLook MVP 내부 고도화 계획

## 한 줄 소개

초행길 운전자는 출발 전에 각 구간의 사진 출처와 경로 일치 상태를 확인하고, 불확실한 안내를 실제 도로 안내로 오인하지 않는다.

## 배경과 문제

- **대상 사용자**: 처음 방문하는 목적지로 출발하려는 운전자
- **문제 상황**: 사진/provider 응답과 경로 간 매칭 근거가 불완전한 상태에서 UI가 정보를 충분히 설명하지 못할 수 있다.
- **기존 대안의 한계**: Demo 화면만 제공되며 provider, 음성, 운전 제한 상태가 앱 흐름에 연결되지 않았다.

## 차량 특화 요소

| 요소 | 내용 |
|---|---|
| 활용하는 차량 데이터·기능 | 현재는 테스트 가능한 Fake 상태. 실제 차량 신호 연결은 별도 승인 후 |
| 주행 맥락 결합 | 출발 전 전체 브리핑, 제한 상태에서는 단순 화면으로 축소 |
| 모바일 대비 장점 | 차량 화면에서 미리 본 구간의 근거와 한계를 분명히 확인 |

## 심사 기준 기여

| 기준 | 이 기능의 기여 |
|---|---|
| 차량특화성 | 주행 제한 상태를 반영하는 화면 계약 |
| 창의성 | 경로·사진·안내의 근거를 함께 보여주는 브리핑 |
| 기술 활용성 (Pleos SDK·API) | SDK 경계와 Mock 동작을 분리하고 실제 미연동을 투명하게 표기 |
| 사업성 | 실데이터 연동 이전에도 반복 가능한 시연 흐름 제공 |

## 사용자 시나리오와 테스트

### 사용자 스토리 1 - 안전한 경로 후보와 사진 매칭 (우선순위: P1) 🎯 시연 MVP

사용자는 경로가 제공하는 geometry와 구간 후보의 근거가 맞는 경우에만 후보를 본다. 정보가 부족하거나 모호하면 일반 안내와 Demo 장면을 확인한다.

**이 우선순위인 이유**: 잘못된 방향·차로 정보를 실제 안내로 오인시키지 않는 것이 핵심 안전 조건이다.

**단독 시연 방법**: synthetic geometry fixture를 사용한 단위 테스트로 정상·실패 매칭을 재현한다. 앱 Demo route는 실제 경로 후보로 승격하지 않는다.

**인수 시나리오**:

1. **Given** 검증된 geometry와 route ID가 맞는 후보, **When** 구간 분석을 수행하면, **Then** 거리·방향·offset 기준을 통과한 후보만 점수화된다.
2. **Given** geometry 부재, source 불일치, 혹은 고가/지상도로 분리가 불가능한 후보, **When** 분석하면, **Then** 구체 차로·회전 안내는 표시되지 않는다.

### 사용자 스토리 2 - 사진 공급 상태와 여러 시점 확인 (우선순위: P1)

사용자는 각 구간의 사진 제공 상태, 출처, 촬영일과 시점 수를 확인하고 가능한 경우 안전하게 시점을 이동한다.

**이 우선순위인 이유**: 실제 provider가 미연동이어도 성공·미지원·오류를 구분해야 한다.

**단독 시연 방법**: Demo 및 Fake provider 상태를 단위 테스트하고 Demo 화면에서 안내 문구를 확인한다.

**인수 시나리오**:

1. **Given** provider가 미설정 또는 사진 없음 상태, **When** 브리핑을 열면, **Then** 사진이 없거나 Demo illustration임을 명시하고 실제 도로 사진이라고 표시하지 않는다.
2. **Given** 2개 이상의 허가된 view 결과, **When** 사용자가 시점을 이동하면, **Then** 유효한 범위 안에서만 시점이 바뀌고 출처·촬영일이 해당 시점과 함께 바뀐다.

### 사용자 스토리 3 - 음성 생명주기와 제한 상태 (우선순위: P2)

사용자는 음성 안내를 끄거나 구간을 이동할 수 있고, 제한 상태에서는 집중을 해치는 탐색 조작이 비활성화된다.

**이 우선순위인 이유**: 주행 상황에서도 목적지 설정 화면 동작을 노출하지 않도록 기반을 만든다.

**단독 시연 방법**: Fake speech output 및 Fake restriction 상태 단위 테스트.

**인수 시나리오**:

1. **Given** 음성이 켜진 브리핑, **When** 구간을 바꾸거나 화면을 나가면, **Then** 기존 발화가 중지된다.
2. **Given** 제한 상태 활성, **When** 제한 UI를 렌더링하면, **Then** 키보드 입력 및 사진 시점 탐색은 제공되지 않는다.

### 주행 상태별 동작

| 상태 | 화면·동작 | 제한 |
|---|---|---|
| 정차 (P단) | 현재 Demo 기능 | 없음 |
| 주행 중 | 제한 안내 및 정적 요약 | 입력·사진 시점 탐색 금지 |
| 시동 꺼짐·재개 | 브리핑 상태 유지 | 음성 자동 재생 금지 |

### 예외 상황

- 차량 신호 미지원: Fake 상태 또는 미연동 문구를 표시한다.
- 권한/SDK 미연결: 실제 provider 호출·차량 연동 없이 Demo를 유지한다.
- 네트워크 끊김: 오프라인/오류 상태를 표시하고 미검증 정보로 fallback한다.

## 요구사항

### 기능 요구사항

- **FR-001**: 앱은 구간 후보의 경로 출처와 매칭 근거를 보존해야 한다.
- **FR-002**: 앱은 위치·방향·경로 offset이 불일치하거나 모호한 후보를 구체 안내에 사용하지 않아야 한다.
- **FR-003**: 앱은 provider 성공·미지원·권한 없음·오류·사진 없음 상태를 구분해야 한다.
- **FR-004**: 앱은 view별 출처와 촬영 시점을 표시하고 시점 이동을 유효 범위로 제한해야 한다.
- **FR-005**: 앱은 구간 변경, 음성 OFF, 브리핑 이탈 시 이전 발화를 중지해야 한다.
- **FR-006**: 앱은 운전 제한 상태에서 입력과 사진 탐색 UI를 제한해야 한다.
- **FR-007**: Demo 데이터 및 제한 상태는 실제 데이터/차량 상태와 구분되어야 한다.

### 사용하는 Pleos SDK·API (예상)

| 필요한 것 | 예상 SDK | 비고 |
|---|---|---|
| 실제 운전 제한 | Android `CarUxRestrictions`/Pleos 정책 | 이번 구현은 Fake만; 실제 adapter 미연동 |
| 음성 출력 | Pleos TextToSpeech | 이번 구현은 output contract와 Fake; SDK 미연동 |
| 경로·위치 | NaviHelper/FusedLocation | geometry 계약 및 앱 권한 미확인 |

## 성공 기준

- **SC-001**: geometry/source/거리/heading 실패 fixture 모두 구체 안내 불가로 판정된다.
- **SC-002**: provider 상태별 브리핑 UI가 적절한 출처와 fallback을 표시한다.
- **SC-003**: 음성 전환/중지와 제한 상태가 단위 테스트에서 검증된다.
- **SC-004**: Demo 전체 흐름과 시스템 라이트/다크 테마가 유지되고 빌드 및 단위 테스트가 통과한다.

## 가정

- 현재 Demo 이미지와 경로는 실제 도로 데이터가 아니다.
- 사용자 승인을 기다릴 필요 없이 Mock 기반 내부 구현과 테스트를 진행한다.
- 외부 API·차량용 표시 권한이 확인되기 전에는 provider를 미설정 상태로 유지한다.
